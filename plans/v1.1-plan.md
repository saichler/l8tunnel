## 1. Features

### 1.1 mTLS agent authentication (C-3)

**Goal:** agents can authenticate with a client certificate instead of (or as
well as) a bearer token, so no secret string lives in `agent.yaml`.

- The relay keeps an internal agent CA (key and certificate in the bbolt
  store, created on first use).
- `l8tunnel-server agent-cert issue --token laptop [--days 365] --out laptop`
  writes `laptop.crt` / `laptop.key`. The certificate carries the token ID
  (URI SAN `l8tunnel:token:<id>`) and a serial recorded on the token.
- The control SNI requests (doesn't require) a client certificate. A
  verified certificate identifies the token; `Hello.token` may then be empty.
  Revoking the token revokes its certificates (serials are checked on every
  handshake, so no CRL distribution is needed).
- Token policy option `require_cert: true` makes the certificate mandatory
  (token alone refused).
- Agent config: `cert:` / `key:`; `token:` becomes optional when set.

### 1.2 Custom domains (H-6)

**Goal:** serve a tunnel at `app.mydomain.com` (CNAME to the relay) as well
as `<name>.<base-domain>`.

- Agent tunnel option `domains: [app.mydomain.com]` (http and tls tunnels).
- The operator must allow them: token policy `domains: ["*.mydomain.com"]`
  (patterns). A tunnel requesting a domain its token doesn't allow gets
  FORBIDDEN. Domains are unique across the relay (NAME_TAKEN otherwise).
- Routing: SNI and Host lookups consult a domain → tunnel map alongside
  `<name>.<base>`; the Host/SNI match rule (421) applies per domain.
- Certificates: ACME HTTP-01 on demand for allowed custom domains
  (`acme.mode` dns01 or http01; dns01 keeps the wildcard for the base domain
  and adds HTTP-01 for custom domains, which needs `listen.http`). With
  static certificates, a custom domain the certificate doesn't cover is
  rejected at registration with a clear error.
- `tls` (passthrough) tunnels need no relay certificate for their domains.

### 1.3 OIDC login for HTTP tunnels (H-7)

**Goal:** protect an HTTP tunnel with "sign in with Google/GitHub/any OIDC
provider" and an allow list, instead of basic auth.

- Providers are configured by the operator in `server.yaml` (secrets stay on
  the relay):
  ```yaml
  oidc:
    providers:
      google: {issuer: https://accounts.google.com, client_id: ..., client_secret: ${GOOGLE_SECRET}}
  ```
- Tunnels opt in from the agent config:
  `oidc: {provider: google, allow_emails: [me@x.com], allow_domains: [x.com]}`.
- One callback URL for the whole relay, `https://auth.<base-domain>/callback`,
  because providers don't accept wildcard redirect URIs. After login the auth
  host redirects back to the tunnel host with a short-lived signed code, and
  the tunnel host sets its own session cookie (HMAC-signed, key in the store,
  `Secure`, `HttpOnly`, `SameSite=Lax`, 12 h by default).
- The relay strips its cookie before proxying and adds `X-L8tunnel-User`
  (verified email) to the request.
- New dependencies: `github.com/coreos/go-oidc/v3`, `golang.org/x/oauth2`.

### 1.4 SSH jump gateway, mode C

**Goal:** `ssh -J gw@tunnel.example.com:2222 user@homebox` with plain OpenSSH,
no helper binary.

- `ssh_gateway: {listen: ":2222", host_key: /var/lib/l8tunnel/gw_host_key}`
  in `server.yaml`; the host key is generated on first start if missing.
- The gateway only relays (`direct-tcpip` channels); no shell, no exec.
  The target host is a tunnel name or `<name>.<base>`, port 22 or the
  tunnel's port; it maps to that tunnel's agent stream. The final SSH
  session stays end-to-end between the client and the private `sshd`.
- Gateway users authenticate with public keys managed on the relay:
  `l8tunnel-server gateway-key add --name alice --key "ssh-ed25519 ..." --tunnels 'home*'`.
- The tunnel's IP lists apply. Tunnels with an access token are reachable
  through the gateway only by keys explicitly granted to them.
- Uses `golang.org/x/crypto/ssh` (already vendored through x/crypto).

### 1.5 HTTP request inspector (O-4)

**Goal:** see (and replay) the requests reaching an HTTP tunnel, like
ngrok's inspector, on the agent's machine.

- Agent option `inspect: 127.0.0.1:4040` (local only; refuses non-loopback
  addresses unless `inspect_public: true`).
- For http tunnels, the agent parses the HTTP/1.1 stream from the relay
  (it's plaintext at the agent) instead of piping bytes blindly, records the
  last N requests/responses (headers plus the first 64 KiB of bodies), and
  passes upgrades (WebSockets) through untouched.
- A small embedded web UI lists requests; "replay" re-sends a request to the
  local target and shows the new response. Live updates over server-sent
  events.
- Off by default; when off, http tunnels keep today's byte pipe.

## 2. Phases

| Phase | Scope |
|---|---|
| **Q1: mTLS agents** | Agent CA in the store, `agent-cert issue`, relay client-cert verification and token mapping, `require_cert` policy, agent `cert`/`key` |
| **Q2: Custom domains** | Protocol field, token `domains` policy, domain map in the registry, routing (SNI, Host, 421), certificates (on-demand ACME, static check) |
| **Q3: OIDC** | Provider config, auth host and callback, signed codes and cookies, per-tunnel allow lists, `X-L8tunnel-User` |
| **Q4: SSH gateway** | Gateway listener, host key, public-key users and grants, `direct-tcpip` to tunnel streams, admin commands |
| **Q5: Inspector** | HTTP-aware agent stream handling, capture buffer, local UI, replay |
| **Q6: Verification** | As in PRD §10.3: every item below tested end to end, real-binary smoke runs (OpenSSH `-J`; OIDC against a local mock provider; custom domain with Pebble), compliance checks, PRD and README updates |

Each phase ends with tests green and a commit; you approve the push, as
before.

## 4. Verification (Q6)

1. **mTLS:** an agent with only a certificate connects; a revoked token's
   certificate is refused; `require_cert` refuses token-only agents; a
   certificate from another CA is refused.
2. **Custom domains:** a CNAME'd domain (simulated with `--resolve`) serves
   the tunnel with a Pebble-issued certificate; a domain outside the token's
   policy is FORBIDDEN; Host/SNI mismatch across domains gets 421.
3. **OIDC:** full login flow against an in-process mock OIDC provider
   (discovery, code exchange, ID token); allow-list rejection; cookie
   tampering rejected; cookie not forwarded; `X-L8tunnel-User` set.
4. **SSH gateway:** real `ssh -J` to a real `sshd` through the gateway;
   ungranted key refused; access-token tunnel reachable only with a grant;
   no shell on the gateway.
5. **Inspector:** requests captured with bodies, WebSocket upgrade still
   works with inspection on, replay produces a new response, inspector
   refuses non-loopback binds by default.
6. Full suite with the race detector, compliance checks, PRD §10.2-style
   traceability updated.

## 5. Decisions needed

1. **OIDC secrets on the relay (recommended) vs in the agent config.** The
   plan keeps provider secrets in `server.yaml` and lets agents pick a
   provider by name. The alternative puts `client_secret` in every
   `agent.yaml`, which spreads the secret and needs one IdP registration per
   agent.
2. **Custom-domain ownership: operator-approved patterns (recommended) vs
   automatic DNS checks.** The plan trusts the token policy. Automatic
   verification (checking that the domain's CNAME points at the relay) is
   possible but fragile behind CDNs and split DNS.
3. **Order.** The plan goes smallest-first (mTLS, domains, OIDC, gateway,
   inspector). If one feature matters most to you, it can move to Q1.
4. **Scope.** All five are independent; any can be dropped or deferred
   without affecting the others.
